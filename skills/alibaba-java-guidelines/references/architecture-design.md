# 工程结构、系统设计与技术文档

## 应用分层

- **[推荐]** 依赖从上层指向下层，不形成环。根据实际架构区分 API/网关、Web/Controller、Service、Manager/应用编排、DAO/基础设施、第三方服务和外部数据边界，不为了“层数”创建空转层。
- Web/Controller 处理协议、认证上下文、基础校验和转换；Service 表达用例/业务事务；Manager/编排层封装第三方、通用能力或多 DAO 组合；DAO 隔离持久化细节。
- **[参考]** 异常在能做出有意义处理的边界转换，日志在统一责任层打印一次。DAO 不重复打印再上抛，顶层转换为受控错误契约。
- **[参考]** DO 映射存储结构，DTO 承载跨边界数据，BO 表达业务对象，Query 表达查询条件，VO 面向展示。不必每层都复制一份对象，只在边界、语义或安全需要时转换。超过两个有语义查询条件时优先封装 Query，不用 Map 传递非类型化契约。

## 依赖和版本

- **[强制]** Maven GAV 表达组织/业务和产品线/模块，不重复语义。自有库版本使用语义化版本，从 `1.0.0` 等可对外表达的稳定起点开始；若采用 `0.x` 预发布语义，必须在发布策略中明确。
- **[强制]** 生产应用不依赖可变 `SNAPSHOT`；已发布版本不覆盖。升级依赖时比对 dependency tree/lockfile，明确验证所有仲裁变化。
- **[强制]** 一组同源组件用统一版本属性/BOM，不在不同子模块中引入相同 GroupId/ArtifactId 的冲突版本。
- **[强制]** 公开库 API 参数使用枚举前考虑扩展性，返回契约不直接暴露会频繁扩展的枚举或包含它的 POJO，避免让调用方因新枚举值失效。
- **[推荐]** 版本声明集中在 `dependencyManagement`/BOM，子模块按需引入。谨慎在底层基础设施引入第三方框架，公共库精简 API 和传递依赖，记录变更和维护者。

## 运行环境

- **[推荐]** 根据并发量、内存、网络和容器/云平台限制设置文件句柄、TCP 和 JVM 参数，不直接照抄手册中面向物理 Linux 服务器的固定数值。
- **[推荐]** JVM 启用 OOM 时堆转储并确保输出位置容量、权限、敏感数据处理和采集流程可用。`Xms=Xmx` 只在固定资源预留和延迟目标合适时采用，容器环境结合限额和 GC 策略实测。

## 设计与文档

- **[强制]** 存储方案和底层数据结构经评审通过并沉淀文档。评审覆盖存储介质、表/字段/索引、容量、性能、数据关系、迁移、兼容、回滚和发布后复核。
- **[强制]** 手册给出的可视化触发基线：交互用户类型超过 1 且用例超过 5 时使用用例图；业务对象状态超过 3 时使用状态图；调用链对象超过 3 时使用时序图；复杂依赖模型类超过 5 时使用类图；多对象复杂流程使用活动图/泳道图。只有图能比文字更清晰时才添加。
- **[推荐]** 架构文档明确系统边界、模块与依赖、主要输入/输出、演进原则，以及安全、可用性、性能、可扩展性、可观测性等非功能要求。
- **[推荐]** 设计不仅覆盖主干，还覆盖异常流程、业务边界、部分成功、超时重试、幂等、降级、补偿和一致性。
- **[推荐]** 类和模块遵循单一职责，优先组合而非继承，依赖稳定抽象，隔离变化点，消除有实际维护成本的重复。不为了形式上套用 SOLID/DRY 而过度抽象。
- **[参考]** 文档首要用于明确需求、理顺逻辑和支持后期维护，指导编码是次要目的。设计的核心是识别并准确表达系统难点；“代码即全部文档”不成立。
- **[参考]** 面向用户的产品考虑键盘聚焦顺序、非视觉验证方式、自定义控件语义和辅助技术兼容。具体实现以当前 WCAG 和平台标准为准。
